## Geiter 项目分析与 P0 开发(v1.22.0)

### 项目本质判断
- Geiter 是「agent 友好的 GEO 测量运行时」,**当前不是 agent**:只测量/提议,`iterate()` 只 claim 动作不执行,provider 契约是问答式。它是agent 的「大脑辅具」,缺主体性(agency)。
- 已有护城河:证据优先(answer hash + 不可用观测留在审计但排除聚合)、确定性回放(jsonl)+ 回归门禁 + 基线对比(自我改进可证伪)、零依赖、机器优先契约。
- 通往「它自己是个 agent」的路线:P0 目标函数+自省 → P1 自主执行最小闭环 → P2 执行器+权限 → P3 记忆复利 → P4 生态。

## v1.23.0 — 跨进程文件锁(解除 P1 阻塞)

分支 `p0/self-inspection` 上完成(未 push)。给所有状态变更方法加**可重入跨进程文件锁**:
- `FileLock` 类:stdlib 零依赖,Windows 用 `msvcrt.locking`、POSIX 用 `fcntl.flock`,sidecar 文件 `.geiter/state.lock`;争用超时抛 `TimeoutError` 而非损坏状态。
- 15 个变更方法加 `@synchronized` 装饰器(init/add/inspect/iterate/record_run_attempt/finish_run/propose_action/claim_action/reclaim_action/resolve_action/add_prompt/record_observation/propose_experiment/approve_experiment/record_experiment_result)。
- capabilities 新增 `concurrency` 契约块;agent-contract.md 新增 Concurrency 章节。

### 关键 bug 与教训(重要)
- **可重入深度必须是线程局部(`threading.local`),不能用实例全局**。初版用 `self._depth` 实例属性,导致共享同一 store 实例的多线程看到 `_depth>0` 直接重入、**完全绕过文件锁** → 写入丢失(20 次 add 偶发丢,1/6 概率)。
- 症状:全量测试偶发 `test_state_lock_serializes_concurrent_writes` 失败;连跑多次才复现。**必须连跑 ≥4 次验证 flakiness,单次全绿不算数。**
- 修复后:`_depth` 与 `_handle` 都改为 thread-local property;10 线程 × 30 次写 = 300/300 精确命中;并发测试连跑 4 次稳定通过。
- 测试有效性验证:去掉 `add()` 的装饰器后 `test_mutating_methods_hold_the_state_lock` 正确失败(证伪实验有效)。注意 spy 特殊方法必须改**类**(`FileLock.__enter__`)而非实例,`with` 语句走类型槽。

### P1 交付(v1.24.0):Geiter 能自己动手了
新建 `geiter/execute.py`(刻意独立模块,不再堆 core.py),实现**自主执行闭环**:
```
introspect → propose(基于证据) → snapshot → apply → re-observe → gate → accept/revert
```
- **`SandboxSurface`**:本地演练知识面(`.geiter/../sandbox/knowledge.md`),每次 apply 前 snapshot,`revert` 是纯文件恢复。
- **`SurfaceProvider`**:读取**活的**知识面生成答案+引用(target 出现在面里才 mention,带 `target:` 前缀才算 target_citation)。**关键**:让门禁评判改动的真实效果,而非 canned 响应——否则自我验证无意义。
- **`execute_cycle()`**:以 regression_gate 为裁判;`gate.ok` 才保留,否则自动回滚并写 `execution.result` learning。
- 接入:CLI `execute --heading --body [--baseline-id --target]`、gateway 工具 `geiter_execute`、capabilities `autonomous_execution` 契约块。
- `.gitignore` 加 `sandbox/`(运行时产物防污染)。

### P1 双向验证(端到端实证)
- **接受路径**:好改动 → gate ok → accepted=True,知识面真实写入。
- **回滚路径**:无 prompts → `prompts_present` 检查失败 → gate 失败 → **自动 revert**,surface 精确恢复,被拒内容不在面上。
- CLI 冒烟 + gateway 测试均通过;70 测试全过(65+5)。

### 关键设计决策(P2 的经验)
- **门禁是唯一裁判**:agent 可自主行动,但无法保留被自己证据否决的改动。这是自主性的安全底座,勿绕过。
- 执行范围严格限本地 sandbox,不碰真实外部内容;后续 P2 若接真实发布,必须加显式 policy 门 + 用户确认。

### 剩余技术债
- `core.py` 约 2000 行 god module(P0/P1 都没再往里堆,但历史负担仍在)。

### P2 交付:策略门 + 人工审批工作流
让 Geiter 能接**真实知识面**而不越界。全部实现在 `geiter/execute.py`。
- **策略门 `SurfacePolicy`**:三级 `auto` / `approve` / `deny`;`allowed_kinds` 限定可改的改动类型(不在集合内视同 deny)。**除 sandbox 外,任何未声明 surface 默认 `approve`**——失误绝不会静默改真实内容。
- **审批工作流**:`request_approval` 持久化 `change.approval_request`(pending_approval),跨进程存活;`decide_approval` 记录具名 approver,已决请求幂等(第一次决定生效,不可覆写);`list_approvals` 按状态查询。
- **`execute_governed`**:deny→直接拒;approve→无批准则建请求并返回 pending(**不碰 surface**);auto 或已批准→走 `execute_cycle` 门禁闭环。
- **核心原则:批准只授权"尝试",不授权"结果"**——批准后仍要过 regression_gate,证据拒绝就回滚。
- 接入:CLI `govern propose|approve|reject|list`、gateway `geiter_govern` + `geiter_approvals`、capabilities `change_governance`(geiter/approvals-v1)。

### 修掉一个真实回归(重要)
